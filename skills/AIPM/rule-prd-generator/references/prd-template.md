## 写作判断

### 事实层级

| 层级 | 写法 | 处理方式 |
|---|---|---|
| 已确认需求 | “本期支持……” | 进入范围、规则和验收 |
| 已知事实 | “当前系统……” | 写明证据或来源，不外推能力 |
| 产品建议 | “建议……” | 说明理由，等待业务确认 |
| 暂定方案 | “本版暂按……” | 写明替换条件和确认节点 |
| 待确认项 | “待确认……” | 不进入确定性验收结论 |

### 优先级

- **P0：** 没有它主流程无法完成、核心价值无法验证，或存在必须解决的权限与安全问题。
- **P1：** 明显改善效率或体验，但不阻断本期主流程。
- **P2：** 后续优化、低频需求或需要额外依赖与运营投入。
- **明确不做：** 与当前目标无关、依赖未成熟或会显著扩大范围的事项。

### 验收标准

验收标准至少包括明确场景、操作或触发条件、可观察结果。可以使用表格，也可以使用 Given/When/Then。优先覆盖：

- 正常主流程；
- 无权限和越权直达；
- 空数据、加载失败和依赖不可用；
- 内容新增、修改、下架后的前后台结果；
- 外部系统失败后的回退；
- 关键数据同步、人工修正和审计记录。

## 交付前快速检查

- 阅读者能否在前两章回答“为什么做、给谁用、这期做到哪里”？
- 同一功能在范围、页面、规则和验收中是否使用同一名称？
- 每个关键页面是否写清入口、内容、操作和离开方式？
- 数据由谁产生、谁维护、多久更新、失败怎么办，是否清楚？
- 权限是否覆盖曝光、列表、搜索、详情、直达链接、图片和附件？
- 外部依赖是否有负责人、验证节点和失败回退？
- 指标是否可计算，建议值是否被误写成正式承诺？
- 待确认事项是否会阻塞设计、研发、测试或上线，最晚何时确认？
