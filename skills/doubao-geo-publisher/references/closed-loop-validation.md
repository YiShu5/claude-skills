# 闭环验证设计

这套 Skill 的闭环验证，不是只看“文章写出来了没有”，而是要看整条链路有没有从接待、生产、发布到监测真正闭合。

## 验证目标

- 证明 Skill 能把客户资料转成结构化交付，而不是停留在聊天建议。
- 证明关键词、Prompt、文章、平台规则和监测计划之间能互相衔接。
- 证明这套流程具备“可复跑、可复核、可迭代”的交付属性，适合上传展示。

## 六道验证关

### 1. 接待诊断关

验证对象：

- 客户资料是否足够进入生产
- 业务场景是否判断正确
- 是否识别出行业敏感点

通过标准：

- `diagnose_client.py` 能输出诊断报告
- 完备度评分不低于 `65`
- 缺口、问题、下一步动作都明确可执行

证据：

- `diagnosis.json`
- `diagnosis.md`

### 2. 关键词策略关

验证对象：

- 是否生成中商业和强商业关键词
- 是否能反映客户真实业务，而不是泛知识词
- 是否符合行业策略，比如教育类不把班型时间词作为主轴

通过标准：

- `generate_geo_plan.py` 成功输出 `geo-plan.json`
- 至少生成 `6` 个可用关键词
- 至少生成 `3` 个文章角度
- `validation_queries` 不少于 `4` 个

证据：

- `geo-plan.json`
- 关键词分层结果
- 文章角度与标题候选

### 3. Prompt 可执行关

验证对象：

- Prompt 是否包含品牌信息、目标关键词、E-E-A-T、平台规则和文章结构
- Prompt 是否能被直接拿去喂给豆包

通过标准：

- 至少生成 `3` 份 Prompt
- 每份 Prompt 都包含：`任务目标`、`品牌与业务信息`、`已验证来源`、`文章结构要求`、`硬约束`

证据：

- `prompts/*.txt`

### 4. 成稿合规关

验证对象：

- 文章是否符合头条 / 搜狐差异化要求
- 是否出现高风险承诺或优化黑话
- 标题和正文是否具备可发布性

通过标准：

- `platform_guard.py` 检查结果无 `error`
- 重点行业如教育、医疗等不出现高风险表达
- 文章保留参考来源段落

证据：

- `article-validation.json`
- `article-validation.md`

### 5. 发布监测关

验证对象：

- 是否生成可执行的回查计划
- 是否能回答“发完以后怎么看效果”

通过标准：

- `build_monitoring_plan.py` 成功输出监测计划
- 至少包含 `4` 个监测词
- 至少包含 `3` 个回查时间点
- 明确人工与自动化分工

证据：

- `monitoring-plan.json`
- 监测字段、节奏、预警规则

### 6. 复盘迭代关

验证对象：

- 是否能根据验证结果判断下一步动作
- 是否形成真正闭环，而不是停在“做完了”

通过标准：

- 必须有一份汇总报告
- 汇总报告里要明确：当前通过项、待补项、建议下一轮内容方向

证据：

- `showcase-summary.md`
- `showcase-summary.json`

## 最终展示时怎么说

上传展示时，建议把闭环描述成这 6 个动作：

1. 诊断客户资料是否能上线
2. 生成关键词与内容策略
3. 自动拼装豆包写作 Prompt
4. 校验头条 / 搜狐发布风险
5. 生成监测计划
6. 输出复盘建议，进入下一轮迭代

## 红黄绿判断

- `绿色`：本轮所有关键关卡都通过，可以直接作为展示案例
- `黄色`：主流程能跑通，但缺少客户证据或成稿，需要补资料
- `红色`：诊断、关键词、Prompt 或平台校验至少有一项失败，不能作为展示案例
